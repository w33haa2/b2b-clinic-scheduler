# API

A JSON API under `/api`, with two separate areas:

| Area         | Prefix                    | Who                    | Route names  |
| ------------ | ------------------------- | ---------------------- | ------------ |
| Clinic API   | `/api/clinics/{clinic}/…` | Members of that clinic | `clinic.*`   |
| Internal API | `/api/internal/…`         | Super admins only      | `internal.*` |

Interactive docs (Swagger, generated by [Scramble](https://scramble.dedoc.co)) are at
**http://localhost/docs/api** in development, with the raw OpenAPI file at `/docs/api.json`.
They do not exist in production (see [Swagger](#swagger-dev-only)).

## Authentication

Laravel Sanctum, two ways:

- **Bearer token** for scripts, mobile apps and Swagger's "Try it":
    ```bash
    curl -X POST http://localhost/api/tokens \
         -H 'Accept: application/json' -H 'Content-Type: application/json' \
         -d '{"email":"admin@example.com","password":"password","device_name":"cli"}'
    # → {"token":"1|…"}
    curl http://localhost/api/me -H 'Accept: application/json' -H 'Authorization: Bearer 1|…'
    ```
    `DELETE /api/tokens/current` revokes the token. Token login is rate-limited
    like the web login (5 attempts per minute per email + IP).
- **Session cookie** for the Inertia frontend: `statefulApi()` is enabled, so
  a user logged in through `/admin/login` can call the API from the browser
  without a token. Every Vue page in the app loads its data this way (see
  [frontend.md](frontend.md#how-pages-get-their-data)).

Always send `Accept: application/json`. Errors use Laravel's JSON shapes: `401`
unauthenticated, `403` forbidden, `404` not found, `422`
`{"message", "errors": {field: [..]}}`.

## Access model

```
request ─► auth:sanctum ─► clinic.member ─► clinic.permission ─► controller
                                (404)            (403)
                                       └─────► clinic.admin ──► controller
                                                   (403)
```

| Middleware          | Rule                                                                                                                     | Failure                                                 |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------- |
| `clinic.member`     | The user has an active membership in `{clinic}` (not removed; clinic not archived).                                      | **404**, so non-members cannot learn the clinic exists. |
| `clinic.permission` | The member's roles grant the permission named after the current route. Clinic Admins pass every check.                   | 403                                                     |
| `clinic.admin`      | The member holds the built-in Clinic Admin role. Used for role and member management, and for editing the clinic itself. | 403                                                     |
| `super-admin`       | `users.is_super_admin` is true. Clinic roles never grant this.                                                           | 403                                                     |

Nested records are bound with **scoped bindings**. For example,
`/clinics/1/patients/9` returns 404 if patient 9 belongs to another clinic.

### Permissions

A permission is a **clinic API route name**. Every route registered inside the
`clinic.permission` middleware group in `routes/api.php` is a permission. The
`clinic_permissions` table is kept in sync automatically: it is rebuilt every
time `php artisan migrate` runs, including deploys and the test suite. To sync
by hand:

```bash
docker compose exec app php artisan clinic:sync-permissions
```

Roles store permissions in `clinic_role_permission`. Built-in roles:

| Role                          | Can be deleted | Can be renamed | Permissions                   |
| ----------------------------- | -------------- | -------------- | ----------------------------- |
| Clinic Admin (`key: admin`)   | No             | No             | All, implicitly (stores none) |
| Clinic Worker (`key: worker`) | No             | No             | Editable. Default: see below  |
| Custom roles                  | Yes            | Yes            | Editable                      |

Default Clinic Worker permissions (defined in `App\Enums\ClinicRoleKey`):
patients index/show/store/update; sessions index/show/store/update and
status.update; session members index/store/destroy, payment.update and
slot.update; session line items index/store/update/destroy; daily sessions
index/show/store/update and patients store/update/destroy; payments index/show and
prepay.store; line-items index/show; members index/show; attendance
index/store/update; discounts index/show/store/update/destroy; payouts
index/show; patient-form.show; patients history.index and progress-notes
index/store/update/destroy; progress-notes index; patient-form-invitations
index/store/resend/destroy.
Workers cannot, by default, see transactions, manage invoices, edit the
catalog, delete attendance, or delete patients, sessions or daily sessions.
The API narrows the payroll ones to the member's own records: a worker
records their own attendance, sees their own payouts, and only ever creates
personal discounts.

Two things are deliberately kept back. **Building the patient form** is not a
worker default — `clinic.patient-form.fields.*`, `clinic.patient-form.reorder`,
`clinic.patient-form.extract.store` and `clinic.patient-form.fields.bulk` —
because it changes what every patient record looks like. It is still
grantable, so an admin can hand it to a role. The **payout settings and
receivables** (`clinic.payout-settings.show`, `clinic.payout-settings.update`
and `clinic.receivables.index`) are `clinic.admin` routes and are not
grantable at all.

The migration `2026_10_31_000016_grant_daily_session_and_payment_permissions_to_workers`
gave the new worker defaults to the Worker role of clinics that already existed.
`2026_11_07_063603_grant_payroll_permissions_to_workers` and
`2026_11_07_103730_grant_patient_module_permissions_to_workers` did the same
for attendance, discounts and payouts, and for the patient module.

A member with several roles gets the union of their permissions.
`GET /api/clinics/{clinic}` returns the current member's effective
`permissions`, so the frontend can hide actions they cannot use.

## Endpoints

### Account

| Method | URL                   | Name             | Notes                                         |
| ------ | --------------------- | ---------------- | --------------------------------------------- |
| POST   | `/api/tokens`         | `tokens.store`   | Email + password + device name → bearer token |
| DELETE | `/api/tokens/current` | `tokens.destroy` | Revoke the token in use                       |
| GET    | `/api/me`             | `me`             | The authenticated user                        |
| GET    | `/api/clinics`        | `clinics.index`  | Clinics the user belongs to                   |

### Clinic API: membership only

| Method            | URL                                                       | Name                        | Notes                                                      |
| ----------------- | --------------------------------------------------------- | --------------------------- | ---------------------------------------------------------- |
| GET               | `/api/clinics/{clinic}`                                   | `clinic.show`               | Clinic + `meta.roles`, `meta.permissions`, `meta.is_admin` |
| GET, POST         | `/api/clinics/{clinic}/calendar-filters`                  | `clinic.calendar-filters.*` | Your own saved schedule filters                            |
| PUT/PATCH, DELETE | `/api/clinics/{clinic}/calendar-filters/{calendarFilter}` | `clinic.calendar-filters.*` | Another member's filter is 404, even for a Clinic Admin    |

Saved filters are personal, so they need no permission. `rules` is
`{"match": "all"|"any", "conditions": [{"field", "operator", "values": [..]}]}`
with `field` one of `staff`, `status`, `type`, `patient`, `payment`, `name`
and `operator` one of `is`, `is_not`, `contains`. The schedule page applies
them; the API only stores them.

### Clinic API: Clinic Admin only (not grantable)

| Method    | URL                                                           | Name                                                           |
| --------- | ------------------------------------------------------------- | -------------------------------------------------------------- |
| PUT       | `/api/clinics/{clinic}`                                       | `clinic.update`                                                |
| GET       | `/api/clinics/{clinic}/payout-settings`                       | `clinic.payout-settings.show`                                  |
| PUT       | `/api/clinics/{clinic}/payout-settings`                       | `clinic.payout-settings.update`                                |

| DELETE    | `/api/clinics/{clinic}/members/{clinicUser}`                  | `clinic.members.destroy`                                       |
| POST      | `/api/clinics/{clinic}/roles`                                 | `clinic.roles.store`                                           |
| PUT/PATCH | `/api/clinics/{clinic}/roles/{clinicRole}`                    | `clinic.roles.update`                                          |
| DELETE    | `/api/clinics/{clinic}/roles/{clinicRole}`                    | `clinic.roles.destroy`                                         |
| GET/POST  | `/api/clinics/{clinic}/invitations` (`{"email"}`)             | `clinic.invitations.index`, `clinic.invitations.store`         |

| DELETE    | `/api/clinics/{clinic}/invitations/{clinicInvitation}`        | `clinic.invitations.destroy` (same rules as the internal ones) |

How a clinic splits its money, and what it has advanced to staff against
patients who have not paid, are the clinic's own books rather than a
worker's business, so neither is grantable. `PUT /payout-settings` takes
`worker_share_percentage`, `include_pending_payments`, `require_attendance`
and `member_shares` as `[{clinic_user_id, share_percentage}]`; a null
`share_percentage` clears that member's override so they follow the clinic
default again. Changing any of it never moves a payout that already exists.
`GET /receivables` filters with `state` (`UNSETTLED` by default, or
`SETTLED` or `ALL`), `clinic_user_id`, `patient_id` and the payout period
(`from` / `to`), and adds `meta.summary` (advanced, settled, outstanding)
and `meta.by_member`.

### Accepting an invitation (web, no sign-in)

The email links to `GET /admin/invitations/{token}` (`invitations.show`,
rate-limited to 20 a minute per IP). Only a SHA-256 hash of the token is
stored. If the invited email already has an account, opening the link adds it
to the clinic (a removed membership is restored) and the page says so. If not,
the page asks for a name and password and `POST /admin/invitations/{token}`
(`invitations.accept`) creates the account (email already verified), joins the
clinic and signs the person in. Expired, revoked, used and unknown links join
nobody.

### Filling in a patient form (web, no sign-in)

`POST /api/clinics/{clinic}/patient-form-invitations` returns a link to
`GET /patient-form/{token}` (`patient-form.show`), throttled with
`throttle:invitations` (20 a minute per IP) like the staff invitation pages.
Only a SHA-256 hash of the token is stored, so the link exists in that one
response and after that only in the message you sent. It sits outside
`/admin` because the person filling it in is a patient, not a member of
staff.

The page renders the clinic's own form, section by section, and
`POST /patient-form/{token}` (`patient-form.submit`) validates the answers
against that same form before saving them, so the public page can never
accept something the API would refuse. With a `patient_id` the link updates
an existing record and opens pre-filled with what it already says, so the
patient corrects rather than retypes; without one it takes on a new patient.
Submitting burns the link: it fills one form in, once.

The page shows one of five states — `open`, `submitted`, `revoked`,
`expired` (after 14 days) or `invalid` for a token that matches nothing.
Posting to anything but an open link redirects back to the page and changes
nothing. Nobody is signed in, so the save is attributed to no member; the
clinic sees `patient_form_invitation.submitted` in its activity log.

## Conventions

- **Responses** are wrapped in `data` (Eloquent API Resources). Every list that
  backs a table is paginated: `?page=` and `?per_page=` (default 25, the
  activity log 30, max 100), with `links` and `meta` (`current_page`,
  `last_page`, `per_page`, `total`, `from`, `to`). The exceptions are short,
  naturally bounded lists, returned whole: roles, permissions, a session's
  patients, a patient's billed items and uninvoiced items, saved calendar
  filters, the patient form's fields, and the user's clinics.
- **Create** returns `201`; **delete** returns `204`.
- **Updates** are partial: send only the fields to change, with PUT or PATCH.
- **Statuses** are upper-case codes: `PENDING`, `ONGOING`, `DONE`,
  `CANCELLED` (sessions); `PENDING`, `DONE`, `REFUNDED` (payments); `INBOUND`,
  `REVERSED` (transactions); `PRESENT`, `ABSENT`, `LATE`, `EXCUSED`
  (attendance); `DRAFT`, `PAID`, `CANCELLED` (payouts); `PERCENTAGE`, `FIXED`
  and `CLINIC`, `WORKER` (a discount's type and the side of the split it
  comes off); `TEXT`, `TEXTAREA`, `NUMBER`, `DATE`, `SELECT`, `MULTISELECT`,
  `CHECKBOX`, `RADIO`, `EMAIL`, `PHONE` (patient form fields); `BASELINE`,
  `IMPROVED`, `UNCHANGED`, `DECLINED`, `RESOLVED` (progress notes).
  `PAST_DUE` is only a payments list filter; a payment has `is_past_due`
  instead. An intake link's `status` is the exception that is lower case
  (`pending`, `submitted`, `revoked`, `expired`): it is derived from
  timestamps rather than stored in a lookup table.
- **Money** is a string with two decimals (`"1500.00"`), never a float.
- **Times** are ISO 8601. Send any offset (`2026-11-02T09:00:00+08:00`). The
  API stores and returns UTC (`…Z`). Use the clinic's `timezone` to display them.
- **Business-rule violations** (e.g. editing a paid item, removing the last
  admin) are `422` with the reason under `errors`.

## Typical flow

1. Super admin: `POST /api/internal/clinics` with `admin`. The clinic gets
   Admin and Worker roles and its first admin.
2. Clinic Admin: add catalog items (`POST /line-items`) and staff
   (`POST /members` with the Worker role ID from `GET /roles`).
3. Worker: create patients, then `POST /sessions` with `clinic_user_id` and
   `patient_ids`; move it `ONGOING` → `DONE`.
4. Bill each patient: `POST /sessions/{s}/members/{m}/line-items`.
5. Record payment: `PUT …/members/{m}/payment` `DONE` (or from `GET /payments`).
   Transactions are written.
6. Invoice the paid items: `GET /patients/{p}/uninvoiced-items`, then `POST /invoices`.

Daily sessions:

1. `POST /daily-sessions` with the holder, default service, window,
   `weekdays`, `starts_on` and `patients` (each with their service and usual
   slot). The next 14 days are scheduled, with patients in their usual slots.
2. Each day: `GET /sessions/{day}` for its patients, `meta.vacancies` and
   `meta.busy`, then `PUT …/members/{m}/slot` to plot whoever is left or to
   change something for that day only.
3. Change someone's regular plan with `PUT /daily-sessions/{d}/patients/{p}`.
4. Pay per day as in step 5 above, or in advance with `POST /payments/prepay`.
5. Past-due days show with `GET /payments?status=PAST_DUE`.

Paying staff:

1. Clinic Admin: set the split with `PUT /payout-settings` — the clinic-wide
   `worker_share_percentage`, whether to pay before the patient does,
   whether to require attendance, and any per-member `member_shares`.
2. Record the working days with `POST /attendance`. A worker records their
   own; an admin records anybody's.
3. `POST /payouts/preview` for a member and a period: the lines that would
   be paid, the totals, and a count of what was left out and why.
4. `POST /payouts` with the same body (plus `exclude_session_line_item_ids`
   to drop lines) creates the DRAFT and locks its items.
5. `PUT /payouts/{p}/status` `PAID` once the member has the money, or
   `CANCELLED` to release the items for another run.
6. Watch what the clinic advanced with `GET /receivables`. A row settles
   itself when the patient's payment is recorded, and re-opens on a refund.

The patient form:

1. Build it with `POST /patient-form/fields`, or import an existing one:
   `POST /patient-form/extract` suggests the inputs it found, and
   `POST /patient-form/fields/bulk` adds the ones you confirmed.
   `PUT /patient-form/reorder` arranges them into sections.
2. Take a patient on either way: `POST /patients` (checked against the same
   form), or `POST /patient-form-invitations` and let them fill in
   `GET /patient-form/{token}` themselves.
3. After each visit, `POST /patients/{p}/progress-notes` with a rating and
   any measurements.
4. `GET /patients/{p}/history` is the whole story. `GET /patients/{p}/pdf`
   prints the record, `GET /patient-form/pdf` a blank form for the desk.

## Swagger (dev only)

- The package `dedoc/scramble` is in `require-dev`. The production image installs
  with `--no-dev`, so the docs routes do not exist there at all.
- Even in development, Scramble only serves the docs when `APP_ENV=local`.
- `config/scramble.php` only overrides a few defaults and must not reference
  Scramble class constants (it is still loaded in production).
- The docs are generated from the code: routes, form requests (validation
  rules become the request schema), API resources (response schema) and
  controller PHPDoc (summaries and descriptions). Keep controller method
  docblocks accurate; they are the endpoint descriptions.
- In "Try it", paste a token from `POST /tokens` into the bearer auth field.

## Adding a clinic endpoint

1. Add the route in `routes/api.php` inside the right group:
   `clinic.permission` (grantable) or `clinic.admin` (Admin only).
   Use a parameter name that matches the parent's relationship (`{patient}` →
   `$clinic->patients()`) so scoped bindings work.
2. Run `php artisan migrate` or `php artisan clinic:sync-permissions`. The
   new permission appears, and Admins can grant it to roles.
3. If Workers should have it by default, add it to
   `ClinicRoleKey::defaultPermissions()`. This only affects clinics created afterwards.
4. Validate in a Form Request with clinic-scoped `exists` rules; return an
   API Resource; throw `ValidationException` for business-rule violations.
5. Add feature tests in `tests/Feature/Api/`.
