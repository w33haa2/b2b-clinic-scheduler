# Frontend

All frontend code lives in `resources/js` and is one Inertia + Vue 3 app,
written in TypeScript. Entry point: `resources/js/app.ts`.

The app has three areas:

| Area             | URL                         | Who            | Pages                                          |
| ---------------- | --------------------------- | -------------- | ---------------------------------------------- |
| Public site      | `/`                         | Everyone       | `pages/public/` (landing page, patient intake) |
| Clinic workspace | `/admin/clinics/{clinic}/…` | Clinic members | `pages/admin/clinic/`                          |
| Internal tool    | `/admin/internal/…`         | Super admins   | `pages/admin/internal/`                        |

`/admin` sends each user to the right place: super admins go to the internal
tool, members of one clinic go straight into it, and members of several
clinics get a picker (`pages/admin/Dashboard.vue`).

## How pages get their data

Pages are thin Inertia routes (`routes/admin.php`). Their data comes from the
**JSON API** (`routes/api.php`, see [api.md](api.md)), called from the browser
with the logged-in session, the same way a mobile app would use a token. The
API checks permissions on every call, so the UI only has to hide what the user
cannot do.

- **Reads:** `useApiQuery(() => url)` loads after mount, reloads when the URL
  changes, and returns `{ data, loading, error, refresh }`. Pages show skeletons
  while `loading` is true.
- **Forms:** Inertia's `useHttp` posts JSON and fills `form.errors` from a 422,
  so `<FormField :error="form.errors.name">` works like a normal Inertia form.
- **One-off actions** (delete, change status, record a payment): `api.delete(url)`,
  `api.put(url, data)`. Show `error.firstMessage` from an `ApiError` in a toast;
  it is the business rule the API refused, e.g. "A clinic must keep at least
  one Clinic Admin."
- **URLs** always come from Wayfinder: `import { index } from '@/routes/clinic/patients'`
  then `index.url(clinicId, { query: { search } })`.

Inertia's HTTP client sends the `X-XSRF-TOKEN` header, and Sanctum's
`statefulApi()` accepts the session cookie for `/api` requests from the app's
own pages.

### Clinic context

Clinic pages receive a shared `clinicContext` prop (set by
`HandleInertiaRequests` after the `clinic.member` middleware):

```ts
const { clinicId, isAdmin, can } = useClinic();

can('clinic.sessions.store'); // true for admins or if a role grants it
```

Permission names are API route names (see [api.md](api.md#permissions)). Use
`can()` to hide buttons and sidebar items. Each clinic page route also
requires the permission of the list it shows (`clinic.permission:clinic.patients.index`),
so opening a page you may not use returns 403.

`auth.clinics` (every clinic the user belongs to) feeds the clinic switcher.

## The schedule

`pages/admin/clinic/Schedule.vue` is a Google Calendar-style view built on
[FullCalendar 6](https://fullcalendar.io/docs/vue) (`@fullcalendar/vue3` with
the daygrid, timegrid, list and interaction plugins).

- **Views:** day, week, month and agenda, switched from shadcn `Tabs`;
  FullCalendar's own toolbar is off.
- **Events** are the sessions in the visible range (`GET /sessions?from&to`, all
  pages). Event IDs say what they are: `session-{id}`, `daily-{id}` or
  `slot-{sessionMemberId}`. A one-off session shows the title (session name,
  or the patients' names), time, the staff member holding it, and patient
  initials.
- **Daily sessions** show only what is plotted: each patient plotted into a
  day of a daily session is its own event (dotted edge) with a small teal
  badge (`DailySessionBadge`); hovering or focusing the badge says it is a
  daily session, which one and who holds it. Patients not plotted yet do not
  appear on the calendar. A plotted patient can be dragged to move the slot
  (`PUT …/members/{m}/slot`); clicking one opens `DailySessionSheet` for
  that day (see below). The event IDs are `session-{id}` and
  `slot-{sessionMemberId}`.
- **New session** in the side panel books a one-off session
  (`SessionFormDialog`). Daily sessions are created and updated on their own
  page (linked under the button).

### Daily sessions: wizard, timeline and panel

Daily-session screens show **clinic time** (`lib/clinicTime.ts`), because the
hours and usual slots are wall-clock times in the clinic's timezone. The big
calendar stays in the browser's timezone.

- **`DayTimeline`** is a one-day FullCalendar grid of the daily hours for drag
  and drop: cards in a `source` element (`[data-drag-id]`, `data-minutes`) are
  dragged onto a time (FullCalendar's `Draggable`), blocks are moved or
  resized, and dropping a block on the `trash` element takes it off. It runs
  in UTC and draws each clinic "HH:MM" as that UTC time, so the grid always
  shows clinic hours. It is browser-only, loaded with `defineAsyncComponent`.
  Blocks: teal = planned, amber = changed for that day, green = paid; striped
  grey = taken by other sessions. Clicking an empty time emits `pick`
  (click-to-place, for touch screens).
- **`pages/admin/clinic/DailySessions.vue`** (sidebar Schedule → Daily
  sessions, permission `clinic.daily-sessions.index`). Each staff member has
  one daily session, so the page shows who already has one (a "You already
  have a daily session" banner, a "You" badge, staff who have one disabled in
  the wizard) and offers Update instead of a second one. Three views, kept in
  the URL so other pages can link to them: the list (each card shows today's
  plotted/paid progress), the wizard (`?new=1`, `?edit={id}`) and the day
  planner (`?session={id}`: pick a day, then plot it). The day picker always
  starts with Today; on a day the session does not run it says why (weekday,
  not started yet, ended) and links to the next day it runs.
- **`DailySessionWizard`** (inline on that page) creates or updates a daily
  session in four steps: details (hours, repeat days, dates, default service;
  warns when the browser is in another timezone), patients & services (a
  service and price per patient), plan the day, and review (per-day total,
  who leaves). Step 3 makes plotting quick: drag patients onto the timeline
  or click a patient then a time; set each patient's length with one tap
  (15–90 min); nudge the selected patient by 15 minutes; auto-arrange with an
  optional gap between patients. Saving sends one request (`POST`, or `PUT`
  with the full `patients` list, which the API syncs); a 422 jumps back to
  the step with the error.
- **Day status** is shown, not set: the planner says when a day starts or
  finishes on its own, and the only button is "Cancel today" / "Cancel this
  day" (with a confirmation).
- **`DayPlanner`** plots one day: "To plot" cards beside the timeline (drag,
  or click then click a time, or `PlotSlotPopover`), "Fill free time" places
  everyone waiting, and clicking a patient opens a card to change today's
  service, go back to the regular plan, record a payment or refund, or take
  them off today. All of it is for that day only (`customised`). On the current day it
  draws a now line, "Fill free time" only uses the time still ahead, and a
  patient can be added for today only. When updating a daily session, the
  wizard's step 3 has a "Today only" tab with the same planner for
  last-minute changes (saved at once; the regular plan is saved with the
  wizard). It is used
  by the Daily sessions page and by `DailySessionSheet`, the panel the
  calendar opens for a day of a daily session (with a link to the page).
- **Filters** (`ScheduleFilterPanel`, also in a popover on small screens):
  quick filters (session status chips; "One-off sessions" and "Daily
  sessions" checkboxes to hide either kind, at least one stays on; payment)
  and the member's saved
  filters ("My filters"). `CalendarFilterDialog` builds a saved filter from
  conditions on staff, status, type, patient, payment (unpaid, past due, paid,
  refunded) and name, matched with "all" or "any", and stores it with
  `/calendar-filters`. Quick and saved filters apply together, in the browser
  (`lib/scheduleFilters.ts`); the header shows how many sessions they hide.
- **Staff colours:** every member gets a colour (`lib/memberColors.ts`, CSS
  variables `--member-color-0…7` in `app.css`). The side panel lists staff with
  checkboxes to hide or show their sessions, like calendars in Google Calendar.
- **Interactions:** drag across the grid (or click a day in month view) to
  book; drag a session to move it or its edge to resize it. The move is saved
  with `PATCH /sessions/{id}` and reverted if the API refuses (e.g. a double
  booking). Click a session to open `SessionSheet`, which handles status
  changes, adding or removing patients, billing services, payments and refunds.
- **State** that should survive navigation (view, date, hidden staff, quick
  filters, the applied saved filter) lives in the Pinia store `stores/schedule.ts`.
- **Times** are shown in the browser's timezone and sent to the API as UTC.
- FullCalendar needs `document`, so `SessionCalendar.vue` is loaded with
  `defineAsyncComponent` and rendered only after mount (skeleton during SSR).
  It is a separate chunk (~80 kB gzipped) that only the Schedule page downloads.
- Styling: FullCalendar's CSS variables are mapped to the shadcn tokens under
  `.session-calendar` in `resources/css/app.css`, so it follows light/dark mode.

## UI components: shadcn-vue + Tailwind CSS v4

shadcn-vue is configured in `components.json` (style `new-york`, base color
`neutral`, CSS variables, Lucide icons via `@lucide/vue`). Its components are
copied into `resources/js/components/ui/` and are built on reka-ui primitives.

Installed: alert, alert-dialog, avatar, badge, breadcrumb, button, card,
checkbox, collapsible, command, dialog, dropdown-menu, input, input-otp, label,
navigation-menu, popover, scroll-area, select, separator, sheet, sidebar,
skeleton, sonner, spinner, table, tabs, textarea, tooltip.

```bash
docker compose exec vite npx shadcn-vue@latest add hover-card
```

When `add` asks to overwrite an existing component (e.g. `button`), answer
**no** unless you mean to lose local changes.

**Form controls: never use native `<select>`, `type="date"` or `type="datetime-local"`.**
They look different in every browser and ignore the theme. Use:

| Need                      | Component                                                                                                                                                                                           |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Pick one of a few options | shadcn `Select` (`SelectTrigger`, `SelectContent`, `SelectItem`). Item values must be non-empty strings, so use a sentinel such as `"none"` or `"all"` for "no value" and convert it before sending |
| A date                    | `components/form/DatePicker.vue` (v-model `"YYYY-MM-DD"`; `year-navigation` adds month/year dropdowns for birth dates; `clearable`; `max="today"`)                                                  |
| A date and time           | `components/form/DateTimePicker.vue` (v-model in the datetime-local format, 15-minute time slots; convert with `fromDateTimeLocal()`)                                                               |
| A long searchable list    | Popover + `Command`, as in `components/form/TimezoneCombobox.vue`                                                                                                                                   |

The calendar's month and year dropdowns were changed from the generated native
select to the shadcn `Select` (`components/ui/calendar/Calendar.vue`). Keep that
change if you re-add the calendar component.

App-level building blocks to reuse before writing new markup:

| Component        | Use for                                                                                                                                               |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PageHeader`     | Page title, description and an `#actions` slot                                                                                                        |
| `FormField`      | Label + input slot + validation error + hint                                                                                                          |
| `ConfirmDialog`  | "Are you sure?" with a processing state                                                                                                               |
| `EmptyState`     | Empty lists (with the Lottie animation)                                                                                                               |
| `DataPagination` | Pager for every paginated list: "1–25 of 80", rows per page, numbered pages. `v-model:page`, `v-model:per-page`, `:meta`; pair with `usePagination()` |
| `StatusBadge`    | Session, payment, transaction, payout and attendance status colours (`kind="payout"`, `kind="attendance"`)                                            |
| `PatientPicker`  | Search-as-you-type patient select (single or multiple)                                                                                                |

**Tailwind v4:** configuration lives in `resources/css/app.css` (`@theme`,
design tokens, dark variant). Use the semantic tokens (`bg-background`,
`text-muted-foreground`, `border`) so both themes work. The accent colour is
teal (`teal-500/600`). Merge classes with `cn()`. Class order is enforced by
`npm run check:fix`.

## Theme (light / dark)

- `ThemeToggle.vue` is a one-click light/dark switch in the app header, on the
  auth screens and in the landing page header. "System" (follow the OS) is
  still available in Settings → Appearance.
- The choice is saved in `localStorage` and in the `appearance` cookie, so the
  server renders `<html class="dark">` on the next request and there is no
  flash of the wrong theme.
- The switch cross-fades the page with the View Transitions API where the
  browser supports it, and switches instantly otherwise or with reduced motion.
- Both icons are always in the markup and `dark:` classes pick the visible one,
  so server-rendered HTML never mismatches the browser.

## Animations

| Tool                                                   | Where                           | How                                                                                                                               |
| ------------------------------------------------------ | ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| [animate.css](https://animate.style)                   | App page headers, cards, sheets | `animate__animated animate__fadeInUp`; tune with `style="--animate-duration: 0.4s; animation-delay: 80ms"`.                       |
| `revealUp` (custom animate.css animation in `app.css`) | Landing page                    | A 12px rise with fast-out/long-settle easing. Hero elements use the classes directly; sections use `v-reveal="'revealUp'"`.       |

| [Lottie](https://airbnb.io/lottie/)                    | `EmptyState` in the app         | `<LottieAnimation :animation-data="json" />`. The player (`lottie-web` light build, no `eval`) is imported lazily in the browser. |

Everything honours `prefers-reduced-motion`: `v-reveal` and `useParallax` do
nothing, Lottie shows a still frame, and calendar events stop fading in.

Lottie files live in `resources/js/animations/`. `calendar-check.json` is
hand-made (a floating calendar whose check mark draws itself). Replace it or add
more from [LottieFiles](https://lottiefiles.com); check the licence first.

## The landing page

`pages/public/Home.vue` inside `PublicLayout.vue`. The design comes from a
review of clinic-software sites (Jane, Cliniko, Heidi, Carepatron, Pabau,
Nookal, Halaxy and others) and of SaaS sites known for crafted design (Linear,
Attio, Mercury, Stripe, Vercel, Cal.com).

**Design rules**

- **Type:** Fraunces (soft serif) for display headings (`font-display`,
  `text-display`, `text-section`, with tight tracking and italic accents),
  Plus Jakarta Sans for UI and body text (`font-sans`), and JetBrains Mono for
  times, amounts and codes (`font-mono` with `tabular-nums`). The extra fonts
  load from Bunny with `preload: false`, so app pages don't pay for them.
- **Colour:** a warm near-white and one deep-teal accent, with a layered warm
  dark mode. The `.landing` class on the layout redefines the shadcn tokens
  (`--background`, `--primary`, `--border`, …) plus `--surface-sunken`, so
  shadcn components inside pick up the palette. App pages keep the neutral theme.
- **Product, not decoration:** every visual is a Vue mock of real screens
  built with believable sample data (`components/landing/`: `HeroSchedule`
  and the `Tour*` panels inside `MockFrame`). No illustrations, gradient blobs or
  stock icons. Mocks are a single `role="img"` with a description.
- **Structure:** hairline borders and alternating sunken bands separate
  sections. No card grids, no gradient text or gradient CTA band, no pill
  badge above the headline.
- **Honest copy:** no invented customers, counts or certifications. The
  numbers row shows product facts (the permission count comes from the
  database). Add testimonials or compliance badges only once they are real.

## State: Pinia

Pinia is registered in `app.ts`. Use it for client-only state that should
survive Inertia navigation. The schedule store (`stores/schedule.ts`) is the
example to follow:

| Data                                                                         | Where it belongs                                        |
| ---------------------------------------------------------------------------- | ------------------------------------------------------- |
| Data owned by the server (records, the logged-in user)                       | The API (`useApiQuery`) or Inertia props                |
| Form state                                                                   | `useHttp` (API) / `useForm` / `<Form>` (Inertia routes) |
| Client-only state shared across components or pages (filters, view settings) | A Pinia store                                           |
| State used by one component                                                  | Local `ref()`                                           |

## Tables and pagination

Every table is backed by a paginated API list, and every list endpoint takes
`?page=` and `?per_page=` (default 25, max 100). The activity log defaults to 30.

```ts
const { page, perPage, query } = usePagination(25, [debouncedSearch]); // back to page 1 when search changes
const { data } = useApiQuery<Paginated<Patient>>(() =>
    index.url(clinicId.value, {
        query: { search: debouncedSearch.value || undefined, ...query.value },
    }),
);
```

```vue
<DataPagination
    v-if="data"
    v-model:page="page"
    v-model:per-page="perPage"
    :meta="data.meta"
/>
```

`DataPagination` (built on the shadcn `pagination` primitives) shows the
range, a rows-per-page select (10 / 25 / 50 / 100, or `:per-page-options`) and
numbered pages with ellipses. Changing the page size returns to page 1, and if
deleting the last row leaves you past the last page, it steps back.

Short lists that are not tables stay unpaginated:

- roles
- the permission list
- one session's patients and billed items
- a patient's uninvoiced items
- the patient form's fields (`GET /patient-form` and `/patient-form/fields`
  return the whole form, in form order)
- "my clinics"

The schedule loads every session in the visible range with `fetchAllPages()`
(100 per request).

## The patient module

Patients are a collapsible sidebar group of three pages. All three are built
on one definition of the clinic's form:

| Sidebar item   | Page                                   | Permission                    |
| -------------- | -------------------------------------- | ----------------------------- |
| Records        | `pages/admin/clinic/Patients.vue`      | `clinic.patients.index`       |
| Progress notes | `pages/admin/clinic/ProgressNotes.vue` | `clinic.progress-notes.index` |
| Patient form   | `pages/admin/clinic/PatientForm.vue`   | `clinic.patient-form.show`    |

- **Records** lists patients (`GET /patients?with_fields=1`) with one search
  box over name, email and phone. A row opens `PatientSheet`; its menu has
  View, Edit, Progress notes, Send intake link, Download record and Archive.
  "Send intake link" and "New patient" sit in the header.
- **`PatientSheet`** is the record in a read-only side panel, with two tabs.
  **Details** shows the built-in columns, then the clinic's own answers, and
  keeps answers to questions that have since been taken off the form under
  "No longer on the form" — an answer a patient gave outlives the question.
  **History** is one timeline of sessions, progress notes and record changes,
  grouped by day; it is a second request, so it waits until the tab is opened.
- **One form, two places.** `GET /patient-form` returns the clinic's questions
  grouped into sections. `DynamicPatientForm` draws the sections and
  `DynamicFormField` turns one question into the control its type calls for
  (`Select` for a dropdown, `DatePicker` for a date, `Checkbox`, and so on).
  The answers live in one flat object keyed by field key — the shape the API
  reads and writes — so the same two components render both
  `components/clinic/PatientFormDialog.vue` (staff adding or editing a
  patient) and `pages/public/PatientForm.vue` (the patient filling it in
  themselves). A field added in the builder appears in both without a change
  in code.
- **The builder** (`pages/admin/clinic/PatientForm.vue`) has three tabs, kept
  in the URL (`?tab=`): **Form**, **Removed** and **History** (the clinic's
  activity log, filtered to the `patients` category). The Form tab is the
  field list beside a **live preview** — the same definition drawn as a
  disabled `fieldset`, so it is the form as a patient sees it and nothing in
  it can be typed in. Reordering is native HTML5 drag-and-drop (`draggable`,
  `dragstart` / `drop`; no library): drop a field on another to take its
  place, or on a section heading to move it to that section. The arrows in the
  row menu make the same move without a mouse. The new order is drawn at once
  and rolled back if `PUT /patient-form/reorder` refuses it. Built-in fields
  are real columns on the patient record, so they can be relabelled but never
  retyped, rekeyed or removed.
- **Removing a field keeps its answers.** The page first asks how many
  patients have answered (`GET …/fields/{field}/usage`) so the prompt can say
  so, then retries the delete with `?confirm=1` when the API refuses an
  unconfirmed removal. The field moves to the **Removed** tab and comes back
  with its answers on restore.
- **"Import from a file"** (`FormImportWizard`, permission
  `clinic.patient-form.extract.store`) reads a form the clinic already uses
  and suggests the fields in it. Two steps: upload or paste, then review.
  Reading is separate from saving — the upload is parsed in the request and
  thrown away, and nothing reaches the form until the review is confirmed
  (`POST /patient-form/fields/bulk`). It reads CSV, TSV, JSON, HTML, DOCX,
  plain text and text-based PDFs. **There is no OCR:** a scanned page holds no
  text, so the wizard says so and asks for the text to be pasted into the box
  instead. Suggestions the clinic already has are listed but cannot be ticked.
- **The intake link** (`IntakeLinkDialog`, from the Records header or a row)
  hands the form to the patient. Issue one for an existing patient (their
  answers are prefilled, so they correct rather than retype) or for somebody
  new. Only a hash of the token is stored, so **the link is shown exactly
  once**, in the response that creates it; after that it only exists in the
  message you sent. The dialog lists the links already issued as Waiting,
  Filled in, Expired or Cancelled, with resend and cancel.
- **`pages/public/PatientForm.vue`** is where the link lands, inside
  `PublicLayout` and marked `noindex`. It needs no sign-in, so it posts to the
  web route with Inertia's `useForm` rather than to the API, and the whole
  form arrives with the page. It has its own copy for a link that is used,
  expired, cancelled or unknown.
- **"Print blank form"** and **"Download record"** render the same definition
  as a PDF (see [architecture.md](architecture.md#activity-log-and-pdfs)).

## Progress notes

`pages/admin/clinic/ProgressNotes.vue` has two modes, and the choice lives in
the URL (`?patient=`) so a view can be shared and survives a reload:

- **No patient chosen** is the clinic's recent notes, newest first
  (`GET /progress-notes`), filtered by staff member, rating, date range and a
  search box. Picking someone with `PatientPicker` switches modes.
- **A patient chosen** is that patient's whole history
  (`GET /patients/{patient}/progress-notes`), oldest first, with a **trend
  card** above it: the latest rating as a badge, and how many notes improved,
  stayed the same or declined (`meta.trend`). `ProgressTimeline` draws the
  notes themselves.
- **`MetricChart.vue`** draws one measurement over time from `meta.metrics`
  — "Pain" from 8 down to 3 across a month. The rating on a note is a
  judgement; a metric is the number behind it. It is **hand-drawn inline SVG
  on purpose**: no charting library is installed, and dependencies need
  approval before they are added. It is a polyline in a fixed viewBox,
  stretched to the card's width, and it honours `prefers-reduced-motion`.
- A note may be edited or deleted by its author, or by a Clinic Admin.

## Payments

`pages/admin/clinic/Payments.vue` (sidebar "Payments", permission
`clinic.payments.index`) lists every payment (`GET /payments`):

- Four summary cards (Unpaid, Past due, Paid, Refunded) with totals from
  `meta.summary`; clicking one filters the table, like the tabs.
- Past-due rows are tinted and badged "Past due" (`StatusBadge :past-due`).
- Row actions "Mark paid" and "Refund" call the same endpoint as the session
  panels (`PUT …/members/{m}/payment`, permission
  `clinic.sessions.members.payment.update`), after a `ConfirmDialog`.
- "Prepay daily sessions" opens `components/clinic/PrepayDialog.vue`: pick a
  daily session, an enrolled patient and upcoming days (quick picks for the next
  5/10/20). Days already paid or cancelled are disabled. It posts
  `/payments/prepay`.

Invoices only accept paid items, so `InvoiceCreateDialog` lists a patient's
paid, uninvoiced services.

## Invoices: row actions and PDF

Each invoice row has an actions menu (View, Download PDF, Delete), and the
invoice panel has a Download PDF button. `lib/download.ts` fetches
`GET /api/clinics/{clinic}/invoices/{invoice}/pdf` with the session, saves the
file under the server's filename (`INV-000014.pdf`), and turns an API refusal
into a toast. The PDF itself is rendered on the server by dompdf from
`resources/views/pdf/invoice.blade.php`.

## Payouts

`pages/admin/clinic/Payouts.vue` (sidebar Payouts → Payout runs, permission
`clinic.payouts.index`) is what the clinic owes each staff member for the
sessions they facilitated. Every billed item is split into the member's cut
and the clinic's, and can only ever be on one payout.

- **Four summary cards** from `meta.summary`: Draft, Paid, **Advanced, not
  collected** and Cancelled. The three status cards filter the table when
  clicked, like the tabs. The advance card is not a status — it is money paid
  out before the patient paid — so for a Clinic Admin it is a link to
  Receivables instead.
- Filters: the status tabs, a staff member (admins only) and a date range.
- **"Generate payout"** opens `PayoutGenerateDialog`, which works in two
  steps so nothing is written by surprise. First pick the member and the
  period (quick picks for this month, last month and the last 7 days). Then
  `POST /payouts/preview` returns every item the member earned in that range
  with its split, and still saves nothing. Rows can be unticked to leave them
  out of the run; "Generate payout" posts the same period to `POST /payouts`
  with `exclude_session_line_item_ids`, so what was reviewed is what gets
  saved. Changing the member or the dates throws the preview away.
- **A row opens `PayoutSheet`**: how the patients' money was split (gross,
  discounts, the member's cut, the clinic's), what the clinic advanced
  against patients who had not paid, and every billed item the run covers.
  Advanced items are tinted and badged.
- Row actions mark a payout paid, cancel it (which releases its items again)
  or delete a draft, each behind a `ConfirmDialog`.

**Payout settings** (`pages/admin/clinic/PayoutSettings.vue`, Clinic Admin
only) is where that split is configured: the clinic's default share for
staff, a per-member rate that overrides it, whether a payout may include work
the patient has not paid for yet, and whether a day only counts once
attendance says the member worked it. A worked example beside the share shows
what a bill of 1,000 leaves each side. The whole page is saved in one
request, and nothing on it changes a payout that already exists.

**Receivables** (`pages/admin/clinic/Receivables.vue`, Clinic Admin only) is
the money the clinic paid out before it collected it: one row per billed item
that went into a payout while the patient's payment was still pending. Rows
settle themselves when the patient pays, so the page is read-only — three
summary cards (Outstanding, Settled, Total advanced), a per-member breakdown
with a bar each, and the Outstanding / Settled / All tabs.

## Attendance and discounts

Both of these feed the payout split, which is why they are worth reading
together.

- **`pages/admin/clinic/Attendance.vue`** (permission
  `clinic.attendance.index`) holds one record per staff member per working
  day, dated in the clinic's timezone. Present and Late count as worked;
  Absent and Excused do not — so when the clinic requires attendance for
  payouts, only the days that count as worked are paid. Four cards count the
  days per status for the current filters and filter the table when clicked.
  The page opens on the current month, and on your own days unless you are a
  Clinic Admin. `AttendanceFormDialog` records a day; only a Clinic Admin may
  write attendance for somebody else, and the member and the date are fixed
  once the row exists.
- **`pages/admin/clinic/Discounts.vue`** (permission
  `clinic.discounts.index`) lists what can be taken off a patient's bill, by
  scope: Clinic-wide (anybody may use it, only an admin may create or change
  one) or Personal (the viewer's own — the list never returns anybody
  else's). A discount is a percentage or a fixed amount, and the column that
  matters is **"Comes out of"**: `CLINIC` means the clinic absorbs it and the
  staff member is still paid on the full price, `WORKER` means the staff
  member absorbs it and the clinic keeps its full cut. That one choice is
  what decides how a billed item is divided on a payout. Who may use a
  discount is fixed when it is created, so an edit never sends the scope.
  Deleting archives.

## Adding a clinic page

1. Make sure the API endpoints exist ([api.md](api.md#adding-a-clinic-endpoint)).
2. Add the page to `ClinicHomeController::PAGES` (route name → required
   permission). `routes/admin.php` registers a `Route::inertia` for each entry,
   guarded by that permission.
   A page that shows the clinic's own books or configuration goes in
   `ClinicHomeController::ADMIN_PAGES` instead. That constant holds route
   names only, and `routes/admin.php` registers each one with the
   `clinic.admin` middleware rather than a permission, so those pages are
   never grantable permissions and no role can open them — only a Clinic
   Admin can. Receivables and Payout settings are the two there today.
3. Create `pages/admin/clinic/<Name>.vue`: call `useClinic()`,
   `setLayoutProps({ breadcrumbs })`, load data with `useApiQuery`, and hide
   actions with `can()`.
4. Add the sidebar item in `AppSidebar.vue` (`clinicNav`) with the same
   permission, or behind `is_admin` for an `ADMIN_PAGES` page.
5. Add a test in `tests/Feature/Admin/AdminPagesTest.php` if the routing rule is new.
